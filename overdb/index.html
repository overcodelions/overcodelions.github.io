Every query, every plan, every environment.

Open a table. Filter it. Fix a value. The everyday work, done carefully.

A first look, one click
Clicking a table asks for 200 rows. On DynamoDB it asks for 5 items, so a quick look never turns into a paid full-table scan. Results stop at 10,000 rows unless you raise the limit.
Filters that cover the whole table
Filtering or sorting a column runs the query again on the server, with your statement wrapped rather than rewritten. The answer covers every row, not just the ones already loaded.
Edit a value in place
A cell is editable only when its row can be found by a primary key or unique index, so an update changes exactly one row. The value is bound, never pasted into SQL, and you see the statement before it runs.
NULL is not empty
NULL and an empty string look different in the grid, and every copy format says what it does with NULL. Only JSON keeps it exactly.
Errors with the fix attached
Mistype a column and overdb matches it against the schema, so id becomes er_id in one click. Anything more than a typo can go to your AI for a repair, which lands in the editor.

Describe the query you want. Read it before it runs.

The plan river

Rows are the water. Slow queries are where it spills.

A plan table hides the two things that make a query slow. Thrown-away rows are a filtered percentage six columns from the count it applies to. Nested loops are a loops number you multiply by hand. Overdb draws the main line of the plan as a stream as wide as the rows moving through it, so both show up at a glance.

width is rows · narrowing is waste · flare is a loop

Performance

Not a prettier plan tree. The step doing the work.

Under the river is the ledger: every step's rows per run, times the runs, multiplied out into the work it does — the sum a plan table leaves you to do in your head, and where a nested loop's cost hides. Alongside it: what the server itself spends time on across every client, from pg_stat_statements or performance_schema, measured from when you opened the pane.

Environments

Run it once. Read every answer.

An environment set is the same logical database across environments, pinned to a baseline: orders-db on local, staging, and two prod regions, where prod-us is the truth. A query fans out to every member, and each one reports its own result. One server timing out doesn't cancel the other three.

The plans diverge

prod-us reads all of orders, where staging narrows it with orders_customer_idx. Each server's plan is laid side by side, step against step, so the one that took the long way stands out. Ask your AI why, and any index it proposes lands in the editor for you to read.

Branches per ticket

A database for every ticket. Seed it, break it, throw it away.

Build a base once: a small, real copy of a dev, sandbox or staging database, running on a server overdb starts on this machine. Then every ticket gets a branch — a clone of the base on its own port, with its own connection — to seed, break and throw away. A proxy sits where your services already connect, and one click in the title bar points them at whichever branch you're working on.

All of it runs on your machine, on 127.0.0.1 — not a shared dev box anyone else can reach. The shared dev, sandbox or staging server is only the source: overdb reads it once to build the base, and never writes to it. A branch is named for whatever you're doing — a ticket key like PROJ-123, an experiment, an idea — and there's no tracker to connect.

orders-db base

Copied from staging: every table, the rows for your tenant and logins, and everything tied to them.

Create a base
overdb reads the catalog, finds the tenant — the table most others point at — and asks which tenant and logins you work with. Every table is sorted with a reason and a size: rows for your starting points, copy whole, start empty, leave out, or schema only. The recipe saves to .overdb/baseline.json in your repo.
Built on its own server
MySQL and MariaDB are copied into a server of the same kind; Postgres and Redshift into Postgres. overdb starts that server itself, with its own directory and port, and never touches yours. It only ever sends reads to the server it copies, and never copies from production or from an untagged server.
Branches you can throw away
A branch is a clone of the base with its own connection in the sidebar, nested under the one it came from. On macOS the clone is copy-on-write, so it's instant and nearly free; elsewhere it's a full copy of the base. Reset puts it back to the base in seconds.
How to connect
Each branch has a How to connect guide built from its own address: use it in overdb, point one service at it (.env, JDBC, the mysql client — the password never shown), or switch every service through the proxy below.
macOS first
Bases and branches are built for macOS today. The background helper that keeps the proxy running when overdb is closed is a macOS LaunchAgent, and servers install through Homebrew. Everything else on this page runs on Windows and Linux too.

a base once · a branch per ticket · on your machine · never from prod

The services proxy

One connection, local or remote. Switch what's behind it in one click.

Every base gets a proxy: one address your services keep, forwarded to the database you pick. Point a service at it once, and from then on the same port reaches the shared dev or staging server the base was copied from, or any local branch of it — no .env to edit, no service to restart, no second set of credentials to juggle. When you're done with a ticket, one click sends your services back to the shared server.

Your services never change. What's behind them does.

The proxy forwards byte for byte. Switching closes the connections it carries, and each service's pool reconnects to the new target on its own. A base copied from a shared server forwards to that server directly when no branch is chosen, with TLS passed through and the certificate still checked against the server's real name — so the same port is your staging database one minute and your ticket's branch the next.

A service that uses two databases is switched in two places: every base has its own proxy, the title bar lists them all, and ⌥⌘0 sends every one back. It moves your services only, never what an overdb tab is querying, and What services see is a read-only connection to exactly where they point.

Remote or local, one port
The same address reaches the shared dev, sandbox or staging server, or any branch of its base on this machine. MySQL proxies default to :3310, Postgres to :5440; a port that's taken says who holds it.
Nothing to reconfigure
Point a service at the proxy once — its .env, a JDBC URL, a Spring profile — and leave it. Switching never needs another change, and the How to connect guide writes the line for you.
Or take over 3306
For your own local server, the proxy can listen on 3306 and /tmp/mysql.sock themselves, so services need no change at all. overdb shows the lines to move your server once and never edits another program's config. macOS only, and it needs the background helper.
Keeps running when overdb doesn't
On macOS, Keep running when overdb is closed moves the proxy and the branches into a small LaunchAgent, removable from the same panel. Without it, quitting asks first while services may still be using the proxy.
Fenced in
Loopback only, one port per proxy, and a proxy for a production connection is refused. A server reached through an SSH tunnel can't be a proxy target itself — its branches still work through the proxy.

one address · remote or local · no .env edits · no restarts · one click back

Only where it's safe
The connection must be tagged local, have writes on, and really be on this machine — no tunnel, and the port held by a database server, not ssh or a cloud proxy. Postgres, MySQL and SQLite can be seeded.
Checked before you see it

Reads the code, carefully
With a linked repo and the claude CLI, the investigation reads your code for what the schema can't say: allowed status values, JSON shapes, app rules. Read, Grep and Glob only — no shell, no MCP servers, and .env files denied. With codex or gemini it plans from the schema alone.
A map of your database

Knows when it's behind
The map records each repo's commit and a fingerprint of each schema, says when it's behind, and Refresh re-reads only the files git says changed. It lives in its own pane beside the diagram, kept on this machine or shared through git in .overdb/map/.

Overlay, not ownership

Read-only until you type the name.

Enabling writes is a setting on each connection, and it stays set, because "this is my local scratch database" doesn't change from day to day. On a connection tagged prod, turning it on asks you to type that connection's name. The mistake worth preventing is running the right statement on the wrong server.

Read-only
engine-level enforcement for SQL databases; fail-closed classification plus read-only IAM for DynamoDB

AI prompts

Four ways in

With no connections yet, overdb offers a server it found answering on this machine, an import from DBeaver, DataGrip, IntelliJ or ~/.pgpass, a blank form that fills itself from a pasted URL, or a sample: one small shop database in local, staging and prod, drifted apart on purpose, so you can see an environment set work before you point it at yours.

Schemas and databases

Switch schema or database from the query header. On MySQL that's a database, on Postgres a schema in the connected database, and the catalog is read again when you switch, so completion stays accurate.

03

Performance you can act on

Every step's estimated rows with the loops multiplied out, so the step doing the work is the one you see. Plans are compared across environments, and Slow queries reads pg_stat_statements or performance_schema from the time you opened the pane, so you can watch a deploy land.

04

ORM placeholders

Paste a statement straight from an ORM log, with ?, :clientName, or #{clientName}, and fill the values in a bar under the editor. Values are bound, never pasted into the SQL, and remembered per environment and per connection.

05

ER diagram

The foreign-key graph, read from the constraints the server holds, plus — dashed, in the AI colour, and cited — the links your database map read from the code. A switch turns those off. It opens on one table and its neighbors, because a 900-table diagram tells you nothing. Export to SVG or PNG.

06

Live health

Sessions and what they're waiting on, connection headroom, cache hit ratio, table sizes, and indexes the planner has never used. When a server won't report a number, overdb says so instead of showing zero.

07

Charts from any result

Line, bar, area, or scatter. Axes and series are picked from the column types, so there's nothing to configure. A null is drawn as a gap, never a zero, and a chart of a truncated result says it's truncated.

08

A grid that stays fast

Rows stream in chunks from a separate process for each connection, and the grid only draws what's on screen. Sorting by a column asks the server again. It doesn't reorder the 1,000 rows you happen to have loaded.

09

History and saved queries

Every statement you run is kept across restarts and grouped with a run count. Search by text, connection, or outcome. Give a statement a name and it becomes a saved query.

10

Fix it in overcli

A plan, or a statement in the slow-query pane, can be handed to overcli to find and fix the code behind it. The statement, plan and findings go; result rows never do. The first send asks which repo uses the database and remembers it.

11

Repos know their schemas

Link any number of repos to a set or a connection, and each says which schemas its code uses. overdb suggests them by scanning for datasource config and schema.table names — names and counts only, with .env and keys never opened — and you confirm.

12

A set that knows who's reachable

Before you press Run, a set's Query tab knows which members it can reach. With one of two on its VPN, Run says Run on 1 of 2 and the other is skipped rather than failed; with none, it says why, in plain words, and points to schema drift, which works from kept catalogs.

Why overdb exists

Four tabs, one query, and a lot of squinting.

Once overgit was handling the repos, the next thing we kept doing by hand was one layer down. Run a query on local. Run it again on staging. Paste it into a prod tab, compare the three results by eye, and hope you're actually connected to the server you think you are.

Overdb makes that comparison the main feature instead of something you do in tabs. It follows the same rules as its siblings: it's an overlay, it's local, and you can check what it does. It doesn't touch a server you didn't point it at, it doesn't send your rows anywhere, and when it isn't sure what a server meant, it tells you.

Before you point it at prod

Questions your DBA will ask.

Most of the answers come down to one thing: overdb reads by default and asks before it writes.

Is it ready to use?

It's v0.2.0 and in beta: an early public build, so expect rough edges and tell us about them in the issues. Everything on this page is in it. Because every connection you add starts read-only, the safest way to try it is exactly how it starts.

What does it cost?

Nothing. Like overcli and overgit, it's Apache 2.0, with no account, no server, and no paid tier. The AI features use a CLI you already have and are already logged in to.

Can it write to prod by accident?

Every connection you add starts read-only; the only ones overdb opens with writes on are the local branches it makes for you. Postgres uses BEGIN READ ONLY, MySQL uses START TRANSACTION READ ONLY, and SQLite opens with its readOnly flag. DynamoDB has no server-side read-only mode, so overdb fails closed on statements it cannot classify; use a read-only IAM policy as the durable boundary. Turning writes on for a prod connection means typing that connection's name. Seeds run only on a connection that is tagged local, has writes on and is really on this machine, and bases, copies and proxies are refused for production and untagged servers. None of those has an override.

Does the AI see our data?

Overdb does not intentionally add result rows or bound parameter values to prompts. Depending on the feature, a prompt can include your question, schema metadata, SQL text, server errors, and plan statistics, so literals or database errors may still contain sensitive values. A ticket you paste into Seed goes too. When you link a repo, the claude CLI reads your code for seeds, bases and database maps with Read, Grep and Glob only — no shell, no MCP servers, and .env and key files denied. The prompt goes to the claude, codex, or gemini CLI already on your machine, and proposed SQL goes into the editor without running.

Which engines are supported?

Ten: PostgreSQL, Amazon Redshift, Aurora PostgreSQL, CockroachDB, and TimescaleDB; MySQL, MariaDB, and Aurora MySQL; SQLite; and Amazon DynamoDB. They run on four drivers, and overdb detects which server it's connected to so it can handle the places they differ, like Redshift having no indexes or MariaDB's performance views. SQL Server, Oracle, and document stores like MongoDB aren't supported.

Where are passwords stored?

In the operating system's encrypted storage, in a separate file from the rest of the app's state. You can also use an environment variable, or a 1Password op:// reference that's resolved when you connect, so the secret is never saved in overdb at all.

⚠ heads up

macOS opens clean: signed with a Developer ID and notarized by Apple, so there's no Gatekeeper prompt. Windows isn't code-signed yet, so SmartScreen may say "unrecognized app" → More info → Run anyway. Bases and branches need a local MySQL, MariaDB or Postgres server, which overdb can install with Homebrew, and database maps need the claude CLI. New to it? Open overdb with no connections and pick the sample: three copies of one small database, drifted apart on purpose.

$ git clone https://github.com/overcodelions/overdb && cd overdb && npm install && npm run dist:mac

— if you'd rather build it yourself.
