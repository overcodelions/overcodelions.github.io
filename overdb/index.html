[ overdb ] · a database client for environments

You don't have a database.
You have environments.

The same schema lives in local, staging and prod, and the interesting questions are comparisons across them. overdb makes that comparison the main gesture — and lets you branch your data like code.

[ the basics ] · everything you'd expect

A full database client. Ask it in plain English, too.

Environments and branches are the reason to switch — but the everyday client comes first: an editor, a grid, your history, and answers in prose when you don't want to write the SQL.

query

  • SQL editor with tabs, and a fast virtualized results grid
  • Ask in plain English — the SQL lands in the editor, nothing runs on its own
  • Schema questions, and Plan and explain for any query
  • Paste straight from an ORM log: ?, :name and #{name} placeholders

explore

  • History of every statement, and saved queries
  • Charts from any result — line, bar, area, scatter
  • ER diagram from real constraints, exported to SVG or PNG
  • Live health and slow queries, from the server itself

connect

  • Postgres, MySQL, SQLite, DynamoDB — and Redshift, Aurora, CockroachDB, TimescaleDB, MariaDB
  • Import from DataGrip, IntelliJ, DBeaver and ~/.pgpass
  • SSH tunnels and TLS
  • Read-only by default; auto-commit or manual transactions

[ one gesture ] · fan out, compare, act

Run it once. See every environment, and what's drifted.

Every member of an environment set answers on its own — a failure on one never aborts the rest — and each answer is compared with the baseline.

[ schema drift ]

Drift ranked by how much it matters.

Compare every member against its baseline, catalog to catalog, without running a statement. Findings are sorted into Breaks, Integrity, Behaviour, Performance and Cosmetic, plus what only one side has — a missing column and a differently-spelled varchar are not the same news.

[ branches ]

Branch your data like you branch your code.

Copy a database to this machine as a small base, then branch it — a writable clone per experiment, made in seconds on macOS. Seed it with exactly the data you need, break it, reset it. Nothing you do in a branch touches the server.

[ the proxy ] · one connection, any branch

Switch the data. Your services don't change a thing.

Point each service at the proxy once. From then on, which data it sees is a click in the title bar — your own server or any branch. The proxy forwards byte for byte, closes its connections on a switch, and every service's pool reconnects to the new one. After that first time, no .env edits and no restarts — a switch drops open connections, and each pool reconnects.

  • ⌥⌘1–9 picks a branch · ⌥⌘0 sends everything back
  • Moves your services only — never what a tab is querying
  • Loopback only, one proxy per base, and refused for production
  • On macOS, can keep running in the background when overdb is closed

[ plans ]

The query as a river.

Rows are the water: the stream narrows where the server throws rows away and flares where a nested loop turns one row into thousands. Those two events are why a query is slow — and in a plan table they are invisible.

The work this query does

The stream is the rows. It necks down where the WHERE clause throws them away — those are the flecks falling out of it — and flares where a loop reads many rows for each one arriving. A ≈ marks a count the server estimated rather than measured. Thickness is on a square-root scale; the numbers on the labels are exact.

[ safety ]

Read-only until you mean it.

Writes are turned on per connection. On prod you type its name first, because the accident worth preventing is doing the right thing to the wrong server.

[ faq ]

Questions people ask.

Is it ready to use?

It's v0.2.3 and in beta: an early public build, so expect rough edges and tell us about them in the issues. Everything on this page is in it, and bases, branches and the background proxy are built for macOS first. Because every connection you add starts read-only, the safest way to try it is exactly how it starts.

What does it cost?

Nothing. Like overcli and overgit, it's Apache 2.0, with no account, no server, and no paid tier. The AI features use a CLI you already have and are already logged in to.

Can it write to prod by accident?

Every connection you add starts read-only; the only ones overdb opens with writes on are the local branches it makes for you. Postgres uses BEGIN READ ONLY, MySQL uses START TRANSACTION READ ONLY, and SQLite opens with its readOnly flag. DynamoDB has no server-side read-only mode, so overdb fails closed on statements it cannot classify; use a read-only IAM policy as the durable boundary. Turning writes on for a prod connection means typing that connection's name. Seeds run only on a connection that is tagged local, has writes on and is really on this machine, and bases, copies and proxies are refused for production and untagged servers. None of those has an override.

Does the AI see our data?

Overdb does not intentionally add result rows or bound parameter values to prompts. Depending on the feature, a prompt can include your question, schema metadata, SQL text, server errors, and plan statistics, so literals or database errors may still contain sensitive values. A ticket you paste into Seed goes too. When you link a repo, the claude CLI reads your code for seeds, bases and database maps with Read, Grep and Glob only — no shell, no MCP servers, and .env and key files denied. The prompt goes to the claude, codex, or gemini CLI already on your machine, and proposed SQL goes into the editor without running.

Which engines are supported?

Ten: PostgreSQL, Amazon Redshift, Aurora PostgreSQL, CockroachDB, and TimescaleDB; MySQL, MariaDB, and Aurora MySQL; SQLite; and Amazon DynamoDB. They run on four drivers, and overdb detects which server it's connected to so it can handle the places they differ, like Redshift having no indexes or MariaDB's performance views. SQL Server, Oracle, and document stores like MongoDB aren't supported.

Where are passwords stored?

In the operating system's encrypted storage, in a separate file from the rest of the app's state. You can also use an environment variable, or a 1Password op:// reference that's resolved when you connect, so the secret is never saved in overdb at all.
