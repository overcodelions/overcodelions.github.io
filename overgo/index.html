[ why overgo ] · what changes when agents belong to the org

An agent that belongs to the org, not to a laptop.

On a laptop, an agent is one person’s helper and forgets when the session ends. On overgo it’s a colleague the whole org can reach — one that remembers, holds only the access its job needs, and answers to a manager.

a worker

It gets better at your org’s version of the job.

Every job, every “useful” or “not useful”, every note its manager adds goes into its journal, and it reads the journal before the next job. It learns its tools — the projects, statuses and people its job uses — and reads the org’s handbook. Its Access tab holds its tools, their scope and how much it does alone, and every change has a history you can restore.

a team

A crew of specialists, each with its own keys.

Put specialists together and a coordinator plans who does what. Each keeps its own tools, scopes and who-can-ask, so the analyst reads the warehouse, the builder pushes branches, and neither can do the other’s job. The team keeps what it knows — the roadmap, customers, what’s decided — and refreshes it weekly.

[ the basics ] · the overcli you know, for everyone

A colleague with one job. Reachable from anywhere.

A worker is a job description with flows, a journal, a manager, a trust level and a budget behind it. On overgo, everyone in the org can ask one — and nobody has to keep a Mac awake for it.

ask

  • Mention @overgo in any channel, or DM it — it finds the worker that can look it up
  • /worker, /team, /hire and /idea in Slack
  • The web console: Inbox, Library, Workers, Teams, Processes, Reports
  • Claude Code, Claude Desktop and Codex through MCP
  • “Keep me posted” in a thread, or Notify me, and it DMs you when there’s an answer
  • Keep talking in the thread after the work is done — it picks up where it left off
  • Sit a worker in a channel: it reads along and answers in the thread only when it can help

work

  • Schedules, and triggers: a new ticket, a webhook, a field that changed, an alarm
  • Approvals in the thread they came from — once per run, not per step
  • Pull requests opened for you, and a red CI build goes back to the worker to fix
  • Act on a run from its live view — approve it, answer it or carry on — with its logs a click away
  • Change how a worker works by saying so — “run the tests before you push” — within what it could already do
  • How much it does alone: Asks first, Trusted, On its own
  • Everything delivered lands in the Library, with time and cost

control

  • Tools installed once for the org, signed in once, scoped per worker
  • Budgets per worker, per person and for the org
  • Passwords, keys and tokens kept out of what workers say
  • Who can ask each worker: its manager, its team, or everyone
  • Every change to the rules in a decision log
  • Export a worker — job, flows, tools, even its journal, keys removed — and bring it to another server
  • Tool requests go to an admin, and a tool that stops signing in alerts them
  • A Monday digest for every manager: each worker’s week, and what waits on them
  • Reports count pull requests: spend per PR, and time saved

[ processes ] · teams and people, stage by stage

The work between teams has a shape. Draw it once.

A process is a series of stages, each a team, a worker, or people who decide. A customer’s problem goes from a channel to a reproduced bug, a fix, a yes from whoever’s on call, a reply the customer can read, and a check a week later — and nobody has to chase it.

In overcli too: Processes is a Lab in the desktop app — build one from your own teams, then publish it to the org.

from a picture

Found a flowchart, a swimlane or a slide? From an image drafts the process from it — boxes as stages, decisions as people deciding, rework arrows as send-backs — and saves nothing until you do.

a library

Eleven to start from — bug to fix, customer escalation, security response, postmortems, launch readiness, experiments, onboarding, pricing and more — each says why every stage is there.

who decides

A decision can be one person, a group, all of them, or at least N. A send-back or a stop from anyone acts at once. Approvers are matched by Slack id, never by a display name.

who sees it

Private, a team, certain people, or everyone. People outside a process see only an outline, and an item, its history and its files are shown only to the people in it.

[ databases ] · from overdb

Your databases, for workers — read only, every query logged.

In overdb, Publish to your org’s server… sends a connection without its password, with what workers should know: the tenancy rule, your notes and the map of your code. An admin finishes it on Setup → Databases. Workers query it through overdb’s read-only tool, and each query is logged by worker and run — the SQL and the row count, never the rows. [ run it yourself ] · one container

Your server. Your keys. Your data.

Build the image from the Dockerfile in the repo — Claude Code inside, Codex if you ask for it. Nothing about your org is in it; it all lives on your volume. The signed image is private while overgo is in alpha: ask for read access, log in to ghcr.io with a read:packages token, and pull it instead. A build of your own isn’t signed by our release workflow. Slack is optional: add its two tokens on Setup → Secrets when you want it. Java, Node, Python or Go install from Setup → Toolchains — no rebuild.

# 1 · get the code and say which model to use
git clone https://github.com/overcodelions/overcli && cd overcli
cp deploy/.env.example deploy/.env      # ANTHROPIC_API_KEY=…, or Bedrock / Vertex
echo "OVERCLI_VERSION=local" >> deploy/.env

# 2 · build the image (add --build-arg INSTALL_CODEX=1 for Codex)
docker build -f deploy/Dockerfile -t ghcr.io/overcodelions/overcli-server:local .

# 3 · start it, and say who the org is
docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml exec overcli \
  overcli org init --name "Acme" --admin <your Slack member ID>

# 4 · sign in: the log prints a one-time first-admin link
docker compose -f deploy/docker-compose.yml logs overcli | grep "first admin"

The console listens on 127.0.0.1:7420 — on a laptop, open it there; on a server, reach it over an SSH tunnel or your VPN’s reverse proxy. To upgrade, check out the new release, build again with the same tag, and docker compose up -d on the same volume. On a Mac, keep /data on the named volume, not a bind mount.

Alpha, and what’s still open. Workers run as a user of their own — on in the compose file by default — so they can’t read the server’s secrets, the tool gateway’s key or people’s tokens, and command tools’ tokens are sealed in the server. Two things a worker can still reach: the model’s credentials its CLI needs, and on EC2 or Compute Engine, the instance’s cloud identity — keep that role to Bedrock or Vertex and the secrets prefix. The security page covers the rest.

[ faq ]

Questions your team will ask.

Do you host it for us?

No. overgo is the org server for overcli, and you run it: one container, on a laptop, a VM, Docker, Fargate or Cloud Run. Nothing about your org is in the image — workers, journals, tokens and the rules all live on your own /data volume. There is no overgo account, and nothing calls home except an optional daily check for a newer release (OVERCLI_UPDATE_CHECK=0 turns it off).

What does it cost?

Nothing from us. It’s in the overcli repo under Apache 2.0, with no seats and no paid tier. You pay for what the workers use: a model key, or Bedrock or Vertex through your cloud account, and every worker, person and the org has a budget, so scheduled work stops at the limit.

How is it different from overcli?

Same engine, different front door. overcli is the desktop app: one person, on their Mac, approving in the app. overgo runs the same workers, teams, flows and processes on a server, so everyone in the org can ask in Slack, the console or Claude, and each worker’s manager approves from wherever they are. Build in the app; publish to the org when it’s ready to share.

Is it ready?

It’s an alpha. It works end to end and it changes quickly between versions — back up /data. In the desktop app, org features stay off until you turn on Settings → Labs → Org workers.

Is it safe to run?

Safer than it was, and still alpha. Workers run as a user of their own, so they can’t read the server’s secrets, the tool gateway’s key or people’s tokens, and command tools’ tokens are sealed in the server; every file read is kept to a run’s own folders. What a worker can still reach: the model’s credentials its CLI needs, and on EC2 or Compute Engine the instance’s cloud identity, so keep that role narrow. Trust levels, narrowed commands, budgets, tool scopes, the tool gateway and the decision log are all on the security page.

Do we need Slack?

No. Slack is optional: without it, people use the web console, or Claude Code, Claude Desktop and Codex through MCP. With it, Slack connects outbound over Socket Mode, so the server needs no public address.

Does it work with Microsoft Teams?

Not yet. Slack is the chat front door today. Without Slack, people use the web console, or Claude Code, Claude Desktop and Codex through MCP.

Do workers push to main?

Never. Workers run no git: the model edits files in its own worktree, and the server commits and pushes an overcli/<change> branch once the repo’s tests pass, then opens its pull request on GitHub or Bitbucket — as a draft by default, for review, or as a link only. It reads the repo’s own CI, and a red build goes back to the same worker to fix on the same branch; after a few rounds, its manager hears. A worker that asks first pushes nothing without its manager’s yes, and people review and merge.
